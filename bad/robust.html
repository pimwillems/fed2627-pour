BAD practice — Robust

Content must be reliably interpreted by browsers and assistive technology. This markup fights them instead.

Demo 1
Div soup: no semantic structure

This entire page uses styled <div>s: no <header>, <main>, <nav>, and the “headings” are just bold text. Screen reader users navigate by headings and landmarks — here they find none. Open the rotor/elements list in a screen reader to see the difference.

Demo 2
Duplicate IDs

Both fields below have id="email". The second label points at the wrong field, and scripts and screen readers only ever find the first one. Click the second label and watch the cursor land in the first field.





Demo 3
Custom checkbox with no semantics

Looks like a checkbox, works with a mouse. But it has no role, no state, no keyboard support. A screen reader announces… nothing. It doesn’t even know it exists.

Demo 4
ARIA used to break things

ARIA can remove semantics too. The button below is visible on screen but has aria-hidden="true" — screen readers skip it entirely. The first rule of ARIA: don’t use ARIA when HTML already does the job; the second: never hide interactive content.

Demo 5
Invalid, sloppy markup

The list below has an unclosed tag and a <div> directly inside a <ul>. Browsers guess their way through it; assistive technology gets whatever the guess produces. Paste this page into validator.w3.org and count the errors.
